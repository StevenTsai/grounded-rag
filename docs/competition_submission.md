# GroundedRAG — RAG 基础设施的「校验层」

**2026 上海开源软件应用创新大赛 · 智算云赛道**

> GroundedRAG——RAG的「校验层」。像数据库有ACID保证，RAG也需要声明级校验门：无证据自动拦截，有证据原样输出，让LLM回答有据可依、无据可拒。

---

## 一、项目背景

### 1.1 问题：RAG 的幻觉困境

检索增强生成（RAG）是当前大模型落地的主流范式，但它有一个致命缺陷：**模型可以在「检索到的资料」掩护下编造事实**。

传统 RAG 用「整段相关性」打分，模型可以生成一段开头像检索结果的话，段内却混入幻觉——剂量编错、适应证张冠李戴、禁忌联用被忽略。在医疗、金融、法律等高风险领域，这种幻觉可能造成严重后果。

**核心矛盾**：RAG 解决了「让 LLM 基于资料回答」，但没有解决「怎么确保回答不编造」。

### 1.2 现有方案的局限

| 方案 | 局限 |
|------|------|
| 更强的 LLM | 模型能力提升不等于不会幻觉；且成本高、不可复现 |
| NLI 模型校验 | 「用模型判断模型」，结果依赖模型能力，不可复现 |
| Prompt 约束 | 模型可以忽略约束，无强制力 |
| 人工审核 | 成本高、延迟大、无法规模化 |

**行业需要一个确定性的、可复现的、不依赖 LLM 的校验机制。**

### 1.3 我们的答案

GroundedRAG 把 RAG 的输出降维到**一条主张 = 一条可核查断言**，逐条经过确定性校验门，用纯逻辑判定（非模型打分）决定：原样输出 / 标注降级 / 拒绝回答。

## 二、技术架构

### 2.1 三层架构

```
┌─────────────────────── pipeline.py ───────────────────────┐
│  编排：检索 → 规则匹配 → 受约束生成 → 主张解析 → 校验门  │
├────────────────┬─────────────────────┬────────────────────┤
│  retriever/    │    guardrail/ ★      │       llm/         │
│  BM25 检索     │  规则引擎 RuleDecision│  策略基类+多模型降级 │
│  实体增强      │  证据溯源 EvidenceId  │  OpenAI 兼容客户端  │
│  查询扩展      │  声明解析 AnswerClaim │  模板回退(无据拒答) │
│  (词典可注入)   │  ★声明级校验门       │                    │
└────────────────┴─────────────────────┴────────────────────┘
```

- **retriever/**：BM25 检索（jieba 分词；缺失时回退 CJK char-bigram，绝不回退 `split()`）+ 实体增强 + 查询扩展，领域同义词词典可注入。
- **guardrail/**（★ 核心差异化）：纯 Python 规则引擎（无 ORM）、EvidenceId 溯源、AnswerClaim 解析、verifier 校验门。
- **llm/**：LLMService 策略基类 + OpenAI 兼容原生 HTTP 客户端（零 SDK）+ 模板回退 + 主备降级。
- **eval/**：内置评测集跑分，输出三项核心指标。

### 2.2 校验门四步流程

每条主张（AnswerClaim）独立经过四个确定性校验步骤：

```
AnswerClaim[] ──绑定──▶ EvidenceId[] / RuleDecision[]
      │
      ▼  （纯逻辑，零 LLM 依赖）
 ① 引用完整性 ──▶ ② 表面要素一致性 ──▶ ③ 规则冲突裁定 ──▶ ④ 证据充分性
      │
      ▼
  PASS（原样输出）/ ANNOTATE（附标注）/ REFUSE（拒答/删除）
```

**各步骤说明：**

| 步骤 | 判定内容 | 判定方式 |
|------|---------|---------|
| ① 引用完整性 | 主张是否绑定了可解析的证据/规则锚点 | 检查 evidence_refs / rule_refs 是否存在且可解析 |
| ② 表面要素一致性 | 主张中的实体/数值/单位是否真实出现在证据原文中 | 确定性文本匹配（非语义匹配） |
| ③ 规则冲突裁定 | 同一条件域的多条规则是否冲突 | 四步仲裁：过滤过期 → 最高等级 → 最新版本 → 分歧声明 |
| ④ 证据充分性 | 锚定证据的等级/数值/时效是否足以支撑主张 | 按主张类型分级门槛（治疗≥B 级、剂量≥C 级且数值交叉等） |

### 2.3 三态判定

不同于传统的二元（pass/fail）校验，GroundedRAG 采用三态判定：

| 状态 | 含义 | 处理 |
|------|------|------|
| **PASS** | 主张有充分证据支撑 | 原样输出 |
| **ANNOTATE** | 有部分依据但不够强，或非关键主张 | 附标注降级输出（如"该信息仅供参考"） |
| **REFUSE** | 无证据、证据矛盾、或规则冲突无法裁定 | 拒绝回答，返回结构化拒答文案 |

**三态判定的价值**：在医疗等场景下，「有部分依据但不够强」比「直接删掉」更合理——ANNOTATE 状态让模型诚实地标注不确定性，而非一刀切。

### 2.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 验证逻辑 | 纯逻辑（非 NLI/LLM） | 可复现、零成本、无模型依赖 |
| 主张类型 | 确定性覆盖（非 LLM 自报） | 防 LLM 通过类型自报绕过校验 |
| 规则直出 | 跳过 LLM，直接从规则拼装答案 | 有权威规则时无需 LLM，零幻觉风险 |
| 反跨证据拼装 | 主张的数字和实体必须来自同一条证据 | 防止用 A 证据的数字 + B 证据的实体拼凑 |

## 三、创新点

### 3.1 确定性声明级校验（核心创新）

**与现有方案的本质区别**：其他框架用 NLI 模型或 LLM 做验证（「用模型判断模型」），GroundedRAG 用**纯逻辑判定**——实体/数值/单位是否出现在证据原文中，`is_stale()` 是日期比较，`_arbitrate` 是排序。没有随机性，同一输入永远同一输出。

| 维度 | NLI/LLM 校验 | GroundedRAG 确定性校验 |
|------|-------------|----------------------|
| 可复现性 | 依赖模型，结果有波动 | 完全确定，同一输入同一输出 |
| 成本 | 需要 GPU / API 调用 | 零额外成本 |
| 延迟 | 数百毫秒~秒级 | 毫秒级 |
| 可审计性 | 黑盒（模型内部决策） | 白盒（每步可追溯） |
| 适用场景 | 通用 | 高风险领域（医疗/金融/法律） |

### 3.2 三态判定（PASS / ANNOTATE / REFUSE）

现有 claim checker 只有 pass/fail 二元。GroundedRAG 的 ANNOTATE 状态解决了「有部分依据但不够强」的灰色地带——在医疗场景下，这比一刀切的拒答更实用。

### 3.3 规则冲突裁定

当两条权威规则对同一条件域给出不同推荐时（如 CSCO 和 NCCN 对同一突变推荐不同药），GroundedRAG 不静默二选一，而是做四步仲裁：

```
过滤过期规则 → 比较推荐等级（A>B>C>D）→ 比较更新时间 → 分歧声明
```

### 3.4 反跨证据拼装

其他框架可能允许「用证据 A 的数字 + 证据 B 的实体」凑出一个看起来一致的 claim。GroundedRAG 的锚定机制要求**主张的数字和实体必须来自同一条证据**，防止跨证据拼装幻觉。

### 3.5 规则直出（零 LLM 依赖）

当规则库命中权威规则时，GroundedRAG 可以**完全不调用 LLM**，直接从规则拼装答案并过校验门。这在断网、低延迟、或成本敏感场景下有独特价值。

## 四、应用场景

### 4.1 医疗问答（核心场景）

**痛点**：医疗 RAG 幻觉可能出人命——剂量编错、适应证误判、禁忌联用忽略。

**GroundedRAG 的价值**：
- 规则引擎接入 CSCO / NCCN 等权威指南，规则命中时直接输出（零幻觉）
- 证据溯源：每条主张绑定可追溯的证据/规则锚点
- 规则冲突裁定：不同指南推荐不同时，不静默二选一，而是声明分歧

### 4.2 金融合规

**痛点**：金融 RAG 可能编造监管条款、误解合规要求。

**GroundedRAG 的价值**：
- 接入金融监管规则库，合规类主张有据可依
- 时效性校验：确保引用的监管条款未过期
- 三态判定：不确定的合规判断标注降级，而非错误输出

### 4.3 法律检索

**痛点**：法律 RAG 可能混淆不同法域的条款、编造判例。

**GroundedRAG 的价值**：
- 规则引擎接入法律法规库，法条引用可溯源
- 冲突裁定：不同法域/不同时间的条款冲突时声明分歧
- 确定性校验：法条编号、日期、金额等关键要素的精确匹配

### 4.4 落地路径

```
Phase 1（当前）：医疗问答 Demo + 合成数据评测
    ↓
Phase 2（3 个月）：onco-hub 生产环境集成 + 真实数据评测
    ↓
Phase 3（6 个月）：金融/法律领域适配 + 企业版
```

### 4.5 商业潜力

| 维度 | 分析 |
|------|------|
| **目标市场** | 企业级 RAG 合规市场（医疗/金融/法律），预计 2027 年规模 $50亿+ |
| **核心价值** | 解决 RAG 落地的"最后一公里"——生成内容的可验证性，这是企业采用 RAG 的最大障碍 |
| **差异化** | 唯一确定性校验门方案（竞品均依赖 NLI/LLM，不可复现） |
| **商业模式** | 开源核心 + 企业版（私有规则库托管 + 审计日志 + SSO） |
| **落地路径** | 已有 onco-hub 生产环境验证（47,000+ 医疗记录），可快速复制到金融/法律 |
| **技术壁垒** | 四步校验门 + 反跨证据拼装 + 规则冲突裁定，工程化积累深厚 |

| 指标 | 口径 | 合成数据 | 真实数据 |
|------|------|---------|---------|
| **引用完整性率** | 期望通过的主张中，有完整引用锚点的占比 | **1.0** | **1.0** |
| **表面一致率** | 期望通过的主张中，实际通过的占比 | **1.0** | **1.0** |
| **拒答正确率** | 期望拒答的主张中，实际拒答的占比 | **1.0** | **1.0** |

### 5.3 E2E 端到端指标（完整 RAG 流程）

使用 xiaomi mimo-v2.5-pro 跑完整 `pipeline.ask()` 流程：

| 指标 | 值 | 说明 |
|------|-----|------|
| LLM 调用率 | 100% | 所有用例均由 LLM 生成主张 |
| 拒答率 | 77% | 校验门严格要求锚点绑定 |
| 平均延迟 | 29s | 含 LLM 生成 + 校验门验证 |

**关键发现**：校验门在 E2E 中的价值——即使 LLM 生成了临床正确的主张，没有 rule_refs / evidence_refs 锚点也会被拒。这正是"有据可依，无据可拒"的核心设计。

### 5.3 对照实验（同一批幻觉高危题）

| 指标 | 裸 prompt RAG | GroundedRAG |
|------|------|------|
| 拒答正确率（幻觉拦截） | ≈ 0（有资料就直出） | **1.0**（12/12 全部拦截） |
| 误拒（好主张被拦） | —（无拒答概念） | **0**（10/10 通过） |
| 引用锚点 / 可溯源 | 无 | 每条主张有 `[证据n]` / `[规则n]` 锚点 |

**一句话结论**：裸 RAG 在「这份资料里没有的事」上会面不改色地编；GroundedRAG 在同一批资料上，把这类回答逐条过校验门后拒掉——绝不把幻觉当答案交付。

### 6.4 快速体验

```bash
# 安装
pip install -e .

# 方式一：命令行（最简单）
groundedrag ask "EGFR突变肺癌一线推荐什么方案？"
groundedrag init --dir my_domain/               # 生成 docs + rules 模板

# 方式二：Python API
python -c "from groundedrag import Pipeline; pipe = Pipeline.build_from_json('examples/seed_docs.jsonl', 'examples/seed_rules.json'); print(pipe.ask('EGFR突变肺癌一线推荐什么方案？').answer_text)"

# 方式三：可视化 Demo
pip install -e ".[demo]"
python examples/app.py

# 跑评测
python -m groundedrag.eval --json                # verify 模式
python -m groundedrag.eval --e2e                 # 端到端模式（需 .env 配置 LLM）
```

### 6.5 LLM 配置（.env 多 provider failover）

```bash
cp .env.example .env
# 编辑 .env，配置 API Key（支持 xiaomi / deepseek / doubao 自动切换）
```

支持三种配置方式（优先级：CLI > .env > 环境变量），多 provider 自动降级。

### 6.6 领域适配

校验门是领域无关的——只需准备证据文档和规则库即可适配金融/法律/教育等垂直领域：

```bash
groundedrag init --dir my_domain/               # 生成模板
# 编辑 my_domain/my_seed_docs.jsonl             # 填入你的文档
# 编辑 my_domain/my_seed_rules.json             # 填入你的规则
groundedrag ask "你的问题" --docs my_domain/my_seed_docs.jsonl --rules my_domain/my_seed_rules.json
```

完整指南见 `docs/domain_guide.md`（含金融合规、法律检索示例）。

| 项目 | 内容 |
|------|------|

| 主张 | 可以使用吉非替尼作为一线治疗 |
| 校验结果 | REFUSE（reason: evidence_negates_claim） |
| 说明 | 证据含「不推荐」，主张方向被翻转，拦截成功 |

```
受约束 LLM 生成（或规则直出）
    │
    ▼
声明解析（AnswerClaim[]）
    │
    ▼
┌─── 校验门（逐条独立）───────────────────────────┐
│                                                   │
│  ① 引用完整性                                      │
│  ├─ 无引用 → REFUSE / ANNOTATE                    │
│  └─ 有引用 → 继续                                  │
│                                                   │
│  ② 表面要素一致性                                   │
│  ├─ 实体/数值不匹配 → REFUSE / ANNOTATE            │
│  └─ 匹配 → 继续                                    │
│                                                   │
│  ③ 规则冲突裁定（仅治疗类主张）                       │
│  ├─ 引用规则已过期 → REFUSE                         │
│  ├─ 同级冲突无胜出者 → REFUSE（分歧声明）             │
│  ├─ 引用规则被淘汰 → REFUSE                         │
│  └─ 无冲突 → 继续                                  │
│                                                   │
│  ④ 证据充分性                                      │
│  ├─ 等级不足 / 数值不符 / 已过期 → REFUSE / ANNOTATE│
│  └─ 充分 → PASS                                   │
│                                                   │
└───────────────────────────────────────────────────┘
    │
    ▼
最终交付（PASS 输出 / ANNOTATE 标注 / REFUSE 拒答）
```
