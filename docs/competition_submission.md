# GroundedRAG — RAG 基础设施的「校验层」

**2026 上海开源软件应用创新大赛 · 智算云赛道**

> GroundedRAG——RAG的「校验层」。像数据库有ACID保证，RAG也需要声明级校验门：无证据自动拦截，有证据原样输出，让LLM回答有据可依、无据可拒。

---

## 一、项目背景

### 1.1 从一个生产事故说起

onco-hub 是一个肿瘤医疗数据平台，接入了 CSCO 等权威指南的规则库，用 RAG 给医生提供用药参考。系统上线后遇到一个问题：**LLM 会篡改检索到的指南内容**。

举个真实场景：检索到了"CSCO 指南推荐奥希替尼 80mg 每日一次"，LLM 生成的回答里却写成了"120mg"——剂量被编造了。更隐蔽的是，模型有时候会把 A 指南的适应证和 B 指南的用法拼在一起，生成一条看起来合理但实际不存在的推荐。

我们试过更严格的 prompt 约束、试过让另一个模型做校验（NLI），都不理想：prompt 约束模型可以无视，NLI 校验结果本身也不稳定，同一条输入跑两次可能给不同分数。

**问题的本质**：RAG 解决了"让模型基于资料回答"，但没有解决"怎么确保回答没有编造"。

### 1.2 我们的思路

既然"用模型判断模型"不可靠，那就不用模型——用**纯逻辑**。

把 RAG 的输出拆成一条条原子主张（"奥希替尼推荐剂量 80mg"），每条主张必须绑定可溯源的证据锚点（这条信息来自哪篇文档、哪条规则），然后用确定性规则逐条校验：

- 主张里的数字有没有出现在证据原文里？
- 主张里的药名和适应证是不是来自同一篇文档？（防跨证据拼装）
- 同一个适应证有两条不同指南推荐时，谁优先？

全部是字符串匹配、日期比较、排序——没有模型参与，同一输入永远同一输出。

这个思路在 onco-hub 生产环境验证后，我们把校验门机制独立出来，做成了 GroundedRAG——一个可以接入任何领域的通用 RAG 校验框架。

## 二、技术架构

### 2.1 三层架构

```
┌─────────────────────── pipeline.py ───────────────────────┐
│  编排：检索 → 规则匹配 → 受约束生成 → 主张解析 → 校验门  │
├────────────────┬─────────────────────┬────────────────────┤
│  retriever/    │    guardrail/ ★      │       llm/         │
│  BM25 检索     │  规则引擎 RuleDecision│  策略基类+多模型降级 │
│  实体增强      │  证据溯源 EvidenceId  │  OpenAI 兼容客户端  │
│  查询扩展      │  声明解析 AnswerClaim │  模板回退(无据拒答) │
│  (词典可注入)   │  ★声明级校验门       │                    │
└────────────────┴─────────────────────┴────────────────────┘
```

- **retriever/**：BM25 检索（jieba 分词；缺失时回退 CJK char-bigram，绝不回退 `split()`）+ 实体增强 + 查询扩展，领域同义词词典可注入。
- **guardrail/**（★ 核心差异化）：纯 Python 规则引擎（无 ORM）、EvidenceId 溯源、AnswerClaim 解析、verifier 校验门。
- **llm/**：LLMService 策略基类 + OpenAI 兼容原生 HTTP 客户端（零 SDK）+ 模板回退 + 主备降级。
- **eval/**：内置评测集跑分，输出三项核心指标。

### 2.2 校验门四步流程

每条主张（AnswerClaim）独立经过四个确定性校验步骤：

```
AnswerClaim[] ──绑定──▶ EvidenceId[] / RuleDecision[]
      │
      ▼  （纯逻辑，零 LLM 依赖）
 ① 引用完整性 ──▶ ② 表面要素一致性 ──▶ ③ 规则冲突裁定 ──▶ ④ 证据充分性
      │
      ▼
  PASS（原样输出）/ ANNOTATE（附标注）/ REFUSE（拒答/删除）
```

**各步骤说明：**

| 步骤 | 判定内容 | 判定方式 |
|------|---------|---------|
| ① 引用完整性 | 主张是否绑定了可解析的证据/规则锚点 | 检查 evidence_refs / rule_refs 是否存在且可解析 |
| ② 表面要素一致性 | 主张中的实体/数值/单位是否真实出现在证据原文中 | 确定性文本匹配（非语义匹配） |
| ③ 规则冲突裁定 | 同一条件域的多条规则是否冲突 | 四步仲裁：过滤过期 → 最高等级 → 最新版本 → 分歧声明 |
| ④ 证据充分性 | 锚定证据的等级/数值/时效是否足以支撑主张 | 按主张类型分级门槛（治疗≥B 级、剂量≥C 级且数值交叉等） |

### 2.3 三态判定

不同于传统的二元（pass/fail）校验，GroundedRAG 采用三态判定：

| 状态 | 含义 | 处理 |
|------|------|------|
| **PASS** | 主张有充分证据支撑 | 原样输出 |
| **ANNOTATE** | 有部分依据但不够强，或非关键主张 | 附标注降级输出（如"该信息仅供参考"） |
| **REFUSE** | 无证据、证据矛盾、或规则冲突无法裁定 | 拒绝回答，返回结构化拒答文案 |

**三态判定的价值**：在医疗等场景下，「有部分依据但不够强」比「直接删掉」更合理——ANNOTATE 状态让模型诚实地标注不确定性，而非一刀切。

### 2.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 验证逻辑 | 纯逻辑（非 NLI/LLM） | 可复现、零成本、无模型依赖 |
| 主张类型 | 确定性覆盖（非 LLM 自报） | 防 LLM 通过类型自报绕过校验 |
| 规则直出 | 跳过 LLM，直接从规则拼装答案 | 有权威规则时无需 LLM，零幻觉风险 |
| 反跨证据拼装 | 主张的数字和实体必须来自同一条证据 | 防止用 A 证据的数字 + B 证据的实体拼凑 |

## 三、创新点

### 3.1 确定性校验（核心）

其他框架用 NLI 模型做验证——本质上还是"用模型判断模型"，校验结果本身不可复现。GroundedRAG 不用模型，纯逻辑：主张里的数字有没有出现在证据原文里？实体是不是来自同一篇文档？全是字符串匹配和日期比较。

在 onco-hub 的生产环境里，这意味着：同一份指南、同一个问题，跑一百次结果一样。这对医疗合规场景是刚需——你不能告诉医生"这个推荐90%是对的"。

| 维度 | NLI/LLM 校验 | GroundedRAG |
|------|-------------|----------------|
| 可复现性 | 同一输入可能不同结果 | 完全确定 |
| 成本 | 需要 GPU / API | 零额外成本 |
| 审计 | 黑盒 | 白盒，每步可追溯 |

### 3.2 三态判定

不是简单的 pass/fail。有些主张"有部分依据但不够强"——比如引用了低等级证据，或者非关键事实（分子量）在证据里找不到。一刀切拒答太浪费，直接输出太冒险。ANNOTATE 状态让系统诚实地标注不确定性，附上"该信息仅供参考"再输出。

### 3.3 规则冲突裁定

onco-hub 接入了 CSCO 和 NCCN 两套指南，同一个突变经常推荐不同的药。原来的做法是取最近更新的那个，但有时候两条指南更新时间差不多，系统就偷偷选了一个——医生不知道这个推荐是哪家的。

GroundedRAG 的四步仲裁：先过滤过期规则，再比推荐等级（A>B>C>D），再比更新时间，如果还分不出胜负就直接声明"存在分歧，请结合临床判断"。

### 3.4 反跨证据拼装

这是在生产中踩过的坑：LLM 把 A 文档的剂量数字和 B 文档的药名拼在一起，生成一条"看起来有证据支撑"的主张。GroundedRAG 的锚定机制要求主张中的数字和实体必须来自同一篇文档，从源头防住这种拼装。

## 四、应用场景

### 4.1 医疗问答（已验证场景）

onco-hub 已经接入了 CSCO 指南的规则库，覆盖肺癌、乳腺癌、结直肠癌等主要癌种。GroundedRAG 的校验门在生产环境中解决了几个具体问题：

- **剂量篡改**：LLM 把证据中的"80mg"编成"120mg"，校验门通过数字比对直接拦截
- **适应证张冠李戴**：A 药的适应证被拼到 B 药上，反跨证据拼装机制要求主张中的实体和数字必须来自同一篇文档
- **指南冲突静默输出**：CSCO 和 NCCN 对同一突变推荐不同药时，系统不偷偷选一个，而是声明分歧让医生判断

规则命中时甚至不需要调用 LLM——直接从权威规则拼装答案，零幻觉风险。这在断网或低延迟场景下特别有用。

### 4.2 金融合规（适配中）

金融场景的逻辑和医疗一样：监管规则是确定性的，合规判断不应该由 LLM 随机生成。我们已经准备了金融领域的评测用例（货币市场基金期限限制、集中度限制等），框架的规则引擎可以直接接入金融监管规则库。

### 4.3 法律检索（规划中）

法律条文的引用比医疗更严格——法条编号、修订版本、生效日期都必须精确。GroundedRAG 的时效性校验和精确匹配机制天然适合这个场景。

### 4.4 落地路径

```
已完成：onco-hub 生产环境验证 + GroundedRAG 框架开源
    ↓
下一步：金融/法律领域规则库接入 + 真实场景评测
    ↓
远期：企业版（私有规则库 + 审计日志 + SSO）
```

### 4.5 商业潜力

GroundedRAG 解决的是企业采用 RAG 的一个实际障碍：**生成内容不可验证**。医疗、金融、法律这些行业的共同特点是"出错成本极高"，LLM 生成的内容如果没有可溯源的证据链，业务方不敢用。

目前市面上的 claim checker（RAG-Verifier、Haystack ClaimChecker）都依赖 NLI 模型，结果不可复现，企业没法拿去做合规审计。GroundedRAG 的确定性校验天然适合需要审计追溯的企业场景。

### 5.3 E2E 端到端指标（完整 RAG 流程）

使用 xiaomi mimo-v2.5-pro 跑完整 `pipeline.ask()` 流程：

| 指标 | 值 | 说明 |
|------|-----|------|
| LLM 调用率 | 100% | 所有用例均由 LLM 生成主张 |

| 平均延迟 | 29s | 含 LLM 生成 + 校验门验证 |

**关键发现**：校验门在 E2E 中的价值——即使 LLM 生成了临床正确的主张，没有 rule_refs / evidence_refs 锚点也会被拒。这正是"有据可依，无据可拒"的核心设计。

### 5.3 对照实验（同一批幻觉高危题）

| 指标 | 裸 prompt RAG | GroundedRAG |
|------|------|------|
| 拒答正确率（幻觉拦截） | ≈ 0（有资料就直出） | **1.0**（12/12 全部拦截） |
| 误拒（好主张被拦） | —（无拒答概念） | **0**（10/10 通过） |
| 引用锚点 / 可溯源 | 无 | 每条主张有 `[证据n]` / `[规则n]` 锚点 |

**一句话结论**：裸 RAG 在「这份资料里没有的事」上会面不改色地编；GroundedRAG 在同一批资料上，把这类回答逐条过校验门后拒掉——绝不把幻觉当答案交付。

### 6.4 快速体验

```bash
# 安装
pip install -e .

# 方式一：命令行（最简单）
groundedrag ask "EGFR突变肺癌一线推荐什么方案？"
groundedrag init --dir my_domain/               # 生成 docs + rules 模板

# 方式二：Python API
python -c "from groundedrag import Pipeline; pipe = Pipeline.build_from_json('examples/seed_docs.jsonl', 'examples/seed_rules.json'); print(pipe.ask('EGFR突变肺癌一线推荐什么方案？').answer_text)"

# 方式三：可视化 Demo
pip install -e ".[demo]"
python examples/app.py

# 跑评测
python -m groundedrag.eval --json                # verify 模式
python -m groundedrag.eval --e2e                 # 端到端模式（需 .env 配置 LLM）
```

### 6.5 LLM 配置（.env 多 provider failover）

```bash
cp .env.example .env
# 编辑 .env，配置 API Key（支持 xiaomi / deepseek / doubao 自动切换）
```

支持三种配置方式（优先级：CLI > .env > 环境变量），多 provider 自动降级。

### 6.6 领域适配

校验门是领域无关的——只需准备证据文档和规则库即可适配金融/法律/教育等垂直领域：

```bash
groundedrag init --dir my_domain/               # 生成模板
# 编辑 my_domain/my_seed_docs.jsonl             # 填入你的文档
# 编辑 my_domain/my_seed_rules.json             # 填入你的规则
groundedrag ask "你的问题" --docs my_domain/my_seed_docs.jsonl --rules my_domain/my_seed_rules.json
```

完整指南见 `docs/domain_guide.md`（含金融合规、法律检索示例）。

**关于 NLI 的定位**：确定性校验是底层保障（零依赖、可审计、可复现），NLI 是可选的语义增强层。两者不矛盾——NLI 处理纯逻辑搞不定的"关系型主张"（如" A 比 B 更有效"），但它的结果只作为参考，不替代确定性校验的最终判定。

**愿景**：成为高风险垂直领域的「可信 RAG 事实标准」——让 LLM 在需要可溯源、可审计的场景下做到「有据可依，无据可拒」。

## 附录

### A. 评测用例示例

**案例 1：数值幻觉拦截**

| 项目 | 内容 |
|------|------|
| 问题 | 奥希替尼推荐剂量是多少？ |
| 证据 | 奥希替尼推荐剂量 80mg，每日口服一次 |
| 主张 | 推荐剂量为 120mg |
| 校验结果 | REFUSE（reason: number_mismatch） |
| 说明 | 主张数值 120mg 与证据 80mg 不符，拦截成功 |

**案例 2：证据侧否定翻转**

| 项目 | 内容 |
|------|------|
| 问题 | 一线可以使用吉非替尼吗？ |
| 证据 | 吉非替尼不推荐作为一线标准治疗 |
| 主张 | 可以使用吉非替尼作为一线治疗 |
| 校验结果 | REFUSE（reason: evidence_negates_claim） |
| 说明 | 证据含「不推荐」，主张方向被翻转，拦截成功 |

**案例 3：规则直出（有据可答）**

### B. 校验门判定流程图

```
用户提问
    │
    ▼
检索 + 规则匹配
    │
    ▼
受约束 LLM 生成（或规则直出）
    │
    ▼
声明解析（AnswerClaim[]）
    │
    ▼
┌─── 校验门（逐条独立）───────────────────────────┐
│                                                   │
│  ① 引用完整性                                      │
│  ├─ 无引用 → REFUSE / ANNOTATE                    │
│  └─ 有引用 → 继续                                  │
│                                                   │
│  ② 表面要素一致性                                   │
│  ├─ 实体/数值不匹配 → REFUSE / ANNOTATE            │
│  └─ 匹配 → 继续                                    │
│                                                   │
│  ③ 规则冲突裁定（仅治疗类主张）                       │
│  ├─ 引用规则已过期 → REFUSE                         │
│  ├─ 同级冲突无胜出者 → REFUSE（分歧声明）             │
│  ├─ 引用规则被淘汰 → REFUSE                         │
│  └─ 无冲突 → 继续                                  │
│                                                   │
│  ④ 证据充分性                                      │
│  ├─ 等级不足 / 数值不符 / 已过期 → REFUSE / ANNOTATE│
│  └─ 充分 → PASS                                   │
│                                                   │
└───────────────────────────────────────────────────┘
    │
    ▼
最终交付（PASS 输出 / ANNOTATE 标注 / REFUSE 拒答）
```
