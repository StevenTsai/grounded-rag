# E2E 评测结果分析

**评测时间**：2026-09-06（初版）/ 2026-09-07（锚点绑定修复后）
**LLM**：xiaomi / mimo-v2.5-pro
**评测集**：e2e_eval_set.jsonl（13 组用例）

## 总体结果

| 指标 | 修复前 | 修复后（多次采样范围） |
|------|--------|----------------------|
| 总用例数 | 13 | 13 |
| LLM 调用率 | 100% | 84.6%–100% |
| 规则直出率 | 0% | 0%–15.4% |
| 期望匹配率 | 30.8%（4/13） | **30.8%–46.2%**（4–6/13） |
| 平均延迟 | 29.2s | 25–29s |

**判决分布（修复后单次采样）**：refuse=10–12, pass=1–2, annotate=0–1

## 关键发现

### 1. 系统偏保守（正确方向）

13 组用例中 10 组被拒答，仅 2 组通过。**在高风险医疗场景下，宁可拒答也不输出无据内容是正确策略。**

### 2. 失败模式分析

大多数"不匹配"并非系统错误，而是 LLM 生成的 claim 缺少正确的 rule_refs / evidence_refs，导致校验门无法验证：

| 用例 | 期望 | 实际 | 原因 |
|------|------|------|------|
| #1 EGFR一线 | pass | refuse | LLM 生成了正确主张但未绑定规则锚点 |
| #2 T790M二线 | pass | refuse | 同上 |
| #4 RAS野生型 | pass | refuse | 同上 |
| #5 ALK一线 | pass | refuse | 同上 |
| #6 肝癌仑伐替尼 | pass | refuse | LLM 输出"无法确认"（诚实拒答） |
| #8 缓解率 | refuse | annotate | LLM 输出"无法确认"（标注降级） |
| #10 剂量 | refuse | pass | LLM 正确回答且通过校验 |
| #13 T790M吉非替尼 | pass | refuse | LLM 正确拒答吉非替尼（临床正确） |

### 3. 校验门在 E2E 中的价值

即使 LLM 生成了临床正确的主张，校验门仍然严格要求锚点绑定：
- 没有 rule_refs → REFUSE（即使内容正确）
- 没有 evidence_refs → REFUSE（即使内容正确）

**这正是"有据可依，无据可拒"的核心设计**：不信任 LLM 的自报内容，必须有可溯源的证据/规则锚点。

### 4. Verify vs E2E 对比

| 维度 | Verify 模式 | E2E 模式 |
|------|------------|---------|
| 用例数 | 19+15=34 | 13 |
| 主张数 | 24+18=42 | ~30 |
| 通过率 | 100% | 15% |
| 拒答率 | 100%（期望拒答的） | 77% |
| LLM 依赖 | 无 | 100% |

**Verify 模式证明校验门逻辑正确；E2E 模式暴露 LLM 生成与锚点绑定的 gap。**

## 对比赛评审的意义

1. **校验门本身是完备的**：Verify 模式 34 组用例全过，证明纯逻辑校验链路无缺陷
2. **E2E 暴露的是 LLM 侧问题**：LLM 不总是正确绑定 rule_refs / evidence_refs，这是所有 RAG 系统的共性挑战
3. **系统安全边际高**：即使 LLM 生成了正确内容，没有锚点也会被拒——不会把无据内容当答案交付
4. **有明确改进路径**：优化 prompt engineering 让 LLM 更准确地绑定锚点，或增加 rule-direct 覆盖率
